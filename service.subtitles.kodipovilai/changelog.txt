0.2.525
- The final subtitle swap claimed success it had not verified, and then
  deleted the file the player was still on.

  When a translation finishes, the add-on copies the result to a clean
  <release>.he.srt, hands it to Kodi, and deletes the transient per-chunk slot
  files. It marked that swap successful because setSubtitles() had not raised.
  But setSubtitles POSTS to the video-player thread and returns before the
  stream is registered -- so the stream list read on the next line was the list
  from BEFORE the add, and "select the most recently added stream" selected the
  last SLOT instead. The cleanup then deleted exactly that file. The viewer was
  pinned to a stream whose file no longer existed: no subtitles for the rest of
  playback, and toggling them off and on did not help.

  This was reachable only on a minority of jobs until now, because the path it
  looked for was computed without the quality-tier suffix and therefore usually
  did not exist, which skipped the whole block. Making the finished file
  actually get delivered would have turned that rare failure into the normal
  one. So the swap now counts the streams, waits up to a second for the count
  to really grow, and only then claims success and pins the stream. If the
  count never grows the slot files are KEPT and a warning is logged -- worst
  case a few stale files the cache prune sweeps up, instead of a viewer with no
  subtitles.

  "No player at all" is treated as safe to clean rather than as a failure,
  otherwise every job that outlives playback left its slots behind. And the
  cleanup now escapes glob characters: release names keep their brackets on
  purpose, and glob reads [YTS.MX] as a character class, so for those releases
  it had been silently deleting nothing.

- One success path never reported at all. When the model returns empty or
  echoes the source, the add-on falls back to Google Translate and returns the
  result -- but it returned WITHOUT telling the caller it was done, so the swap
  above never ran and the viewer was left on the slot file holding the very
  output that had just been rejected as not-Hebrew. That is the same "it plays
  the original language" symptom, on the one path nobody had wired.

- A cache marker could be evicted out from under the file it describes. The
  zero-byte '.google' marker says a translation is machine output and must
  never reach the community pool, and '.shared' records that a file was already
  uploaded. Reading a translation refreshed only the translation, so on a file
  watched for years the markers aged out on their own and were deleted while
  the file stayed. After that the add-on no longer knew, and the next play
  could have pushed machine translation into the shared pool. A marker now
  counts as being as recent as the file it belongs to.

- Two labels in the model picker were wrong. "3.1 Flash (premium, 250/day)"
  and "3.8 Flash (newest, heavier quota use)" both have a real free cap of 20 a

0.2.524
- The gender check could rewrite a CORRECT line into a wrong one.

  A feminine verdict on a reference does not merely fail to help -- it ACTS.
  wrong_gender_entries flags the entry, and _regender_blocks then hands the
  model the Hebrew alone with the flat assertion "these address a FEMALE
  listener, but they were written addressing a male". Its only acceptance test
  is that the rewrite no longer says "ata". So a false feminine does not
  degrade gracefully: it rewrites a correct masculine line into a wrong
  feminine one, and nothing downstream can veto it.

  "at" is Hebrew's definite-object marker as well as the feminine pronoun, and
  the old guard only refused it before a he-definite noun. Definiteness is an
  OPEN class -- "at ze", "at kol", "at atzmi", "at ma" -- so no list of
  exceptions ever finishes the job. Measured on a full human episode, 13 of 60
  feminine verdicts were ordinary object marking, one of them on a line whose
  speaker is explicitly male.

  Hebrew MORPHOLOGY has no such ambiguity. The 2fs future/imperative and a
  short list of bare imperatives can only address a woman, and reading those
  adds 23 cues the pronoun alone missed. The pronoun still counts, but only
  when at least one of its occurrences is not followed by an unmistakable
  definite object. Net on that episode: 57 -> 69 verdicts with the 13 false
  ones gone -- precision and recall both improve, which is why this replaces
  the guard rather than extending it.

  Two details that took a measurement to get right: the 1sg past ending -ti
  must not be read as a 2fs imperative, and "kol kach" is "so/very", not an
  object, so "at kol kach yafa" does address a woman.

- Arabic verbs carrying an object pronoun are now read too. Arabic glues the
  object straight onto the verb, and a suffix-must-end-the-word rule missed
  every one of them. The clitic set is closed, so the noun classes refused in
  0.2.523 stay refused -- the six-letter floor blocks those whatever follows.
  It does open one new class, a broken plural carrying a possessive, which is
  structurally identical to a real verb and cannot be separated without a
  lexicon; it is pinned as a test so the trade stays visible rather than being
  rediscovered later as a surprise.

0.2.523
- The Arabic gender reference could not read Arabic.

  Arabic anchors more real jobs than any other reference language -- 41% of
  every job that got one, measured on 5,708 of them. And every pattern this
  module used to read it required HARAKAT. Real subtitles carry none: a full
  human episode has 7,415 Arabic letters and TWO diacritics, and not one
  vocalised anta/anti. So reference_addressee_gender(line, 'ar') returned
  F=0, M=0, None=370 across that entire file. The most-used reader we had was
  the emptiest.

  The 2fs PRESENT suffix is consonantal and always written, so it can be read
  from the text real people actually get. Two noun classes wear the same
  ending and had to be refused: the tafʿil verbal noun (tamrin, taʿyin,
  tahsin, tadkhin) and the feminine sound dual (tafsila -> tafsilatayn). The
  first is FIVE letters and structurally identical to a real five-letter verb,
  so the floor is six letters and three genuine verbs are given up on purpose.
  Recall loses a little; precision wins, and that is the right way round --
  this reader feeds a repair pass, and a false feminine spends a request
  rewriting a line that was already correct.

  Measured on that episode: 0 -> 19 of 370 cues (5.1%), eleven distinct forms,
  every one a genuine second-person feminine verb, with twelve noun controls
  all correctly refused.

- The Hebrew reader was better at finding a MALE addressee than a female one.

  _HE_MASC has always carried the proclitic alternation -- it matches ve-ata,
  she-ata, kshe-ata. _HE_REF_FEM did not, so ve-at, she-at and kshe-at read as
  no pronoun at all. An asymmetry in exactly the wrong direction, in a check
  whose entire purpose is catching masculine-where-feminine. Three more cues
  on the same episode, and the object-marker guard is untouched.

- A guard that was promised and not kept. begin() is documented "Fully
  guarded; never raises" and everything after the candidate fetch sat outside
  every handler, so a candidate the source engine returned in an unexpected
  shape left the function as an AttributeError. The single caller does wrap
  it, so the user outcome was always the correct silent fallback -- but a
  module documented as never raising has to actually never raise.

- Two statements in our own code that were not true. The docstring on
  reference_addressee_gender said only 'ar' and 'he' were read; nine more
  languages have been read from _ADDRESSEE_MARKERS since it landed, and our
  own test exercises all of them. And the alignment comment claimed a random
  pairing votes ~0.30: measured, a true pair votes 0.742, twenty randomised
  starts vote 0.417-0.441, and nine time-reversed references 0.439-0.441. The
  floor is ~0.43. The gate still clears it, by less than we said.

0.2.520
- When there is no embedded subtitle to extract, the log now says WHY instead
  of looking like a failure.

  A report: "why did it fail to extract the embedded subtitle?" The log said

      embedded_extract: no matching text track (num=None lang=en)
      embedded: no usable text track for en

  and nothing else. It had not failed. The file was a BluRay remux, and a
  BluRay carries its subtitles as PICTURES, not text -- so the three subtitle
  tracks the player listed were images of text, and there was nothing for a
  text extractor to take. Falling through to the ordinary subtitle search was
  the correct outcome, not a fallback from an error.

  THE LINE COULD NOT SAY THAT, and three different situations produced it word
  for word: every track is a picture format, the only matching track is flagged
  "forced" (signs only, which is deliberately refused), or the language really
  is absent. Verified by running all of them against the real selector -- same
  line every time. So the reader's next question is always "is our extractor
  broken?", and usually the answer is "that file has no text subtitles".

  It now prints what the file actually contains -- track number, codec,
  language, forced flag -- and then says which of the three it is. The
  inventory is already parsed at that point, so this costs one line and no
  work. Behaviour is unchanged; only the log is.

  AND IT ASSERTS ONLY WHAT IT TESTED, which the first version of this did not.
  It began by treating "no S_TEXT/* track" as "every track is a picture", and
  those are different claims: Matroska has text subtitle codecs that predate
  the S_TEXT/* naming and sit outside it -- S_ASS, S_SSA, S_USF (what older
  muxers wrote), S_HDMV/TEXTST, S_KATE. On such a file the new line would have
  said there was nothing but pictures and that the external search was correct
  "not a fallback from a failure" -- steering the reader away from a real gap,
  in the release whose entire purpose is to stop the log giving a confident
  wrong answer. There is now a list of the codecs that genuinely are pictures,
  and a track outside both sets gets its own line saying it is text this
  extractor does not read yet and is worth investigating. Checked by running
  every codec class through it.

  A language the file does not declare is also marked. The parser substitutes
  'eng' when a track carries no Language element, and printing that as though
  it were declared makes this line disagree with mkvinfo and read as a parser
  bug. It now shows [eng?].

  This one applies to the standalone add-on as well, which ships the same
  extractor.

  on identical rate limits in every table Google publishes -- same tokens per
  minute, same tokens per day, same free requests per day -- so this is a
  drop-in swap exactly like the 3.5/3.6 -> 3.7 move before it, with no change
  to quota use or pacing.

  3.7 still answers, so nothing here was urgent. What is not fine is leaving a
  stored model id the picker no longer lists: the settings screen then shows a
  blank where the model should be. Hence the one-shot migration.

  IT RUNS ON BOTH CHANNELS. The build edition and the standalone (repo-channel)
  add-on do NOT run the same service file, and changelog text is shared between
  them -- so a promise like the one at the top of this entry can be true for one
  and a lie for the other. That is not hypothetical: the 3.7 migration in
  0.2.494 reached the build and never reached the standalone, and survived three
  releases before a user found it by reading the zip. tools/test_channels_agree
  .py now checks this claim against both services, and the 3.8 migration was
  written into both at the same time.

  Each bump gets its OWN marker (`_gemini_model_bump_v3`), never a reused one.
  The previous marker is already set on every device that took the previous
  bump, so reusing it would skip the migration for precisely the users who need
  it. The retired set covers 3.6 and 3.5 Flash too, so the migration is correct
  on its own rather than correct only because of the order two functions happen
  to run in.

  The free-tier daily counter keeps its row for 3.7 even though the picker has
  dropped it. A stored id outlives a dropdown -- a device that has not booted
  since the update, or one restored from a backup, still asks that table for a
  number, and a missing row would silently hand it the Flash-Lite figure of 500
  a day against a real free cap of 20.

  tools/test_gemini_model_table.py is new and holds four tables to one list of
  models: the picker, the daily-cap table, the requests-per-minute pacing and
  what the migrations write. It was written before the change and immediately
  caught two defects in it -- a migration still pointing at 3.7, which the
  picker no longer offers, and a marker count that only looked right.

0.2.516
- temperature and Top-P are no longer sent to the models that stopped
  accepting them.

  Google's Gemini API docs, verbatim: "temperature, top_p, and top_k are
  deprecated and ignored. In future model generations, supplying these
  parameters returns an HTTP 400 error. Remove these parameters from all
  requests."

  Ignored today, a hard 400 tomorrow -- and a 400 on a translation chunk is
  not a worse translation, it is no translation: the request raises and the
  chunk is lost. But the parameters are NOT simply removed, because on Gemini
  2.5 and 3.1 they still do real work, and the build's 1.0 / 0.95 defaults
  were measured on exactly those models. So the rule is per model: 3.5 and up
  send neither, 2.5 and 3.1 keep both.

  ONE PLACE DECIDES. gemini.sampling_params_supported() reads the generation
  out of the model id and both request builders consult it, so a caller may
  keep passing temperature= and top_p= without knowing the rule and a caller
  added later cannot forget it. That matters more than it sounds: the audio
  call SubSync makes for speech intervals lives in subsync.py with a hardcoded
  temperature=0.0, nowhere near the translation code, and is precisely the
  site an if-per-call-site would have missed. It is covered now by
  construction. (top_k is in Google's list too; this add-on has never sent it
  and has no setting for it, so there was nothing to gate.)

  THIS RUNS ON THE STANDALONE TOO. gemini.py and settings.xml are both in the
  repo-channel package, so the gate and the two hidden sliders reach those
  users exactly as they reach the build. Said out loud because the changelog is
  shared between the two editions and a note that does not mention the
  standalone gets filtered out of its package -- which is how a change that
  DID run there ends up announced nowhere.

  A model id with no readable generation -- an alias like
  'gemini-flash-latest' -- also sends neither. That direction is chosen: such
  an alias resolves to whatever is newest, which is where the parameters are
  going away; omitting them is a valid request on every model that ever took
  them; and guessing the other way costs a 400.

  THE TWO SLIDERS ARE GONE FROM THE SETTINGS SCREEN on a model that ignores
  them -- a control that changes nothing is worse than no control. They come
  back on 2.5 and 3.1 with the user's own numbers intact, because the settings
  are still stored and still read; only the request changes. The default model
  is 3.5 Flash Lite, so out of the box neither slider shows.

  The visibility list in settings.xml is a WHITELIST of the models that still
  honour the parameters, not a blacklist of the ones that do not: add a newer
  model to the picker and forget the list, and the slider correctly stays
  hidden. tools/test_gemini_sampling_params.py fails if the list and the code
  ever disagree, builds real payloads through a stubbed requests to prove what
  each model's request actually carries, and catches eight mutants of the rule.

v0.2.456
- Embedded subtitle extraction stops punishing one congestion event six times.
  The pace controller backed off per 429 RESPONSE rather than per congestion
  EPOCH: a single cluster fetch retries up to five times, and every retry that
  answered 429 widened the gap again, so one unlucky cluster could multiply it
  by 1.5^5 on its own. A field log shows the whole failure in thirty-three
  seconds -- first refusal after 68 requests, sixth refusal 27 requests later,
  and the pace at its 2.00s ceiling for the rest of the run. It was overshoot,
  not a slow provider: the same log then records 25 consecutive CLEAN requests
  at that ceiling. Now, after widening, the controller refuses to widen again
  until the new pace has actually been measured, so repeat refusals from the
  same event are honoured and retried without compounding.
- Recovery could not keep up with the back-off either. 0.9x per 25 clean
  requests is one 10% step per fifty seconds at a 2.00s pace, and that run
  managed exactly one such step in its lifetime. Now 0.85x per 12 -- still far
  more cautious than the 1.5x back-off, so it errs slow rather than fast, but
  no longer permanently.
- And it no longer relearns the same lesson every episode. Every extraction
  started at the same optimistic pace, spent the provider's burst allowance
  discovering it was too fast, and paid the climb again. The pace a run settles
  on is now remembered per provider and the next run starts there, 25% quicker
  so it keeps probing and one bad night fades over a few runs. It can never
  start faster than a fresh install would, only slower.
  Measured against the real debrid link from the field log: a 2.79GB BluRay
  REMUX that had reached 143 of 364 cues in four minutes now returns all 364 in
  just over two, with the subtitle complete and no errors.

v0.2.454
- Extracting a built-in subtitle is about twice as fast. It was never limited by
  bandwidth -- it was waiting: one connection, one request at a time, so every
  line cost the gap we deliberately leave between requests AND a round trip to
  the debrid server on top of it, and the link sat idle for most of the four
  minutes an episode took. It now uses three connections while the provider is
  behaving, and -- this is the part that matters -- they all take their turn from
  ONE shared schedule, so the server is still asked at exactly the same rate as
  before. Only our own waiting disappears. Measured at the real settings against
  a typical debrid round trip: an episode goes from about three minutes to about
  one and a half, for exactly the same number of requests.
- It stands down at the first sign of trouble. The moment the provider pushes
  back even once, or the file turns out to be one whose structure has to be
  re-learned as it goes, everything hands back to the single connection and
  finishes the way it always did. That is deliberate: pushback is judged by how
  many refusals pile up against progress, and three connections pile them up
  three times faster -- which would make the add-on give up on exactly the
  awkward-but-usable provider it was taught to patiently crawl through.
- And a fault while fetching can no longer end as a quiet success. If anything
  unexpected goes wrong on one part of the file, that part is now re-read the
  slow, thorough way instead of vanishing from a subtitle that still reports
  itself complete -- which would also have thrown away the saved progress that
  exists to recover it next time.

v0.2.453
- Ktuvit subtitles that arrive unzipped now reach the community pool, and their
  timing can be checked again. The engine converts a downloaded subtitle to
  UTF-8 only when it has just unpacked it from an archive; Ktuvit sometimes
  hands over the .srt on its own, and those files were used exactly as they
  arrived -- in the older Hebrew encoding. Everything that reads a subtitle
  afterwards reads it as UTF-8, so every Hebrew letter turned into a

  the channel), and the timing check saw one line of dialogue instead of
  hundreds and gave up. A downloaded subtitle is now converted whichever way it

- ...and the conversion can no longer damage a file it was not meant to touch.
  "Not valid UTF-8" is not the same as "the old Hebrew encoding": it also

  made into a ruined subtitle. The conversion is now accepted only when it

v0.2.446
- Reading a video's embedded subtitle track over a debrid link now costs about
  half the network requests it used to. Every subtitle line was paying for two
  separate range requests: one at the start of its cluster, purely to work out
  where the line sits and what time it begins, and one for the line itself.
  Neither of those two facts has to be re-read for every line -- the first is a
  property of how the file was muxed, the second is already recorded in the
  file's own index. Both are checked against the old method before they are
  relied on, and anything that does not check out falls back to it, so a file
  can only be read faster, never less accurately.
- A short buffering hiccup no longer cancels an extraction in progress. Kodi

  has to be held for a few seconds to count. Pausing deliberately and then
  resuming still hands the connection straight back to the player, as before.
- An interrupted extraction keeps what it collected, and the next attempt
  continues from there. On a provider that limits requests aggressively an
  extraction can only ever be cut short, so it previously never finished at all,
  no matter how many times the file was played. A partial result is still never

  connection and has no purpose for a local file.

  Such a line appeared several cues early, sat on screen over unrelated dialogue,

v0.2.38
- Four targeted improvements to Hebrew gender (זכר/נקבה) accuracy
  in AI translation. Today the gender form is right ~90% of the
  time; the remaining 10% mostly traces to four specific failure
  modes that these changes address. No behavioural change for any
  non-Hebrew code path.

- (a) Cross-chunk context carry-over: we translate in parallel
  chunks (default 250 entries each). Until now, each chunk was
  translated INDEPENDENTLY: the AI saw the cast block but no
  recent conversational thread, so a character finishing a line
  at the end of chunk N would sometimes get a different gender
  the moment they spoke at the start of chunk N+1. We now feed
  the last 5 SOURCE-text lines of chunk N-1 into chunk N's
  prompt as a "PREVIOUS DIALOGUE CONTEXT" section -- AI sees the
  thread, picks up the gender consistently. The previous chunk's
  source is precomputed up-front (deterministic per index) so
  parallel dispatch still works -- no inter-chunk dependency.
  Tunable via the `prev_context_lines` setting (default 5;
  0 disables the feature).

- (b) Speaker-prefix hints: SRT entries that start with an
  ALL-CAPS speaker tag like "MABEL:" or "DR. SMITH:" used to be
  dropped on instruction ("do NOT include speaker prefixes in
  the Hebrew"). The prompt now tells the AI to MATCH the prefix
  name against the cast block, use that person's gender for
  first-person forms in the line, then drop only the prefix
  from the output. Speaker prefixes are common in SDH /
  Telegram SRTs and were previously thrown away even though
  they're the strongest gender signal we ever get.

- (c) Reply heuristic: in two-character dialogues, short
  follow-up lines ("Right.", "No way.", "You sure?", "I told
  you.") are almost always REPLIES from the OTHER speaker.
  New explicit prompt rule: "speakers alternate unless context
  says otherwise; apply alternation before falling back to a
  gender guess." Catches the most common single-line gender
  flip in dialogue.

- (d) Cast list widened from top-12 to top-25 (`tmdb_helper`
  default). Minor characters (waiters, partners, one-scene
  parents) whose gender mattered for the line they spoke were
  often outside the top-12 cut and defaulted to the AI's
  best guess. Existing cached cast lookups with fewer than
  20 entries are treated as cache misses and re-fetched on
  next translation, so users with prior watches get the
  expanded list automatically without manual cache clear.
