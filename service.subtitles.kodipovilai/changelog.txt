0.3.111
- Faster, lighter provider search (fetching/providers/engine.py). The providers start together: the 100 ms pause before each start (inherited from the vendored DarkSubs engine, nothing depends on the start order) is gone, which cost up to 0.6 s before the last provider even began. The wait loop makes ONE pass over the workers every 60 ms instead of a nested scan every 10 ms, and rebuilds the row list and the status text only when a provider ended or published rows or a second passed. With 7 stub providers answering after 2 s: 2.72 s -> 2.05 s wall and about 0.05 s -> 0 s of loop CPU. The all-language retry is unchanged.
- One requests.Session per provider (fetching/providers/general.ProviderHttp): the calls of one search or download (Ktuvit: login, search, list; the download's identifier and file) reuse their TLS connection instead of a new socket and handshake each. The session keeps connections, never cookies (the providers pass theirs per call, exactly as before), and a session idle for 30 s is replaced. Subscene keeps its own TLS adapter session.
- fetching/providers/cache.py reads its stored values with ast.literal_eval, no eval(): the stored format (a repr) is unchanged, so old entries are still read, and an entry that cannot be read is a cache miss (refetched and rewritten).
- core/contracts.py (never wired) is removed. The contract test keeps the static checks, the every-module-imports pass and the chooser-thread unit check; the golden harness is gone.

0.3.103
- Manual search is a free-text search (VLSub style). The button "חיפוש כתוביות ידני" now asks ONE question, "חיפוש מחרוזת כתובית", pre-filled with the playing release name: edit it, delete words, add a release group or a keyword (FLUX, WEB-DL, x265), or type another title ("Dune 2021", "Show S01E03"). The text is split into a title (with year and SxxEyy) and release words (fetching/manual.parse_query): the title steers the search (TMDB finds its IMDb id; when TMDB has none the search goes by the text), the release words rank the list (rows with every word first, then some, then the rest, nothing is dropped, a toast says when no row has them all). A lone ALL-CAPS word (or a word of the playing release) is a release word: "FLUX" searches the playing video for FLUX releases. The raw text reaches the providers that take text (OpenSubtitles gets it as its query first; Subscene and SubSource search by the title when there is no IMDb id; Ktuvit matches the exact title when there is no IMDb id); Wizdom and YIFY need an IMDb id and BSPlayer hashes the playing file, so BSPlayer is left out when another title is typed. The search caches are keyed by the typed text, so a manual list is never the automatic list of the same title. The head line reads "חיפוש ידני: <text>"; "חזרה לרשימה" brings the automatic list back; the playing video's info is untouched, so a pick is still downloaded, translated, synced and shared with the playing video.
- The chooser paints the words a subtitle's release shares with the playing release in green (resolution, source, video codec, audio, HDR, release group; and the words of a manual query) in the release column and in the info panel (ui/chooser_rows.shared_mask / paint).
- The "תרגום AI" badge is gone from rows that can be AI-translated (that is the normal case); a row that CANNOT be AI-translated says "ללא תרגום AI" with the reason in the info panel: translation switched off, no Gemini key in "ai" mode, embedded-track translation off or local-only on a stream, or an embedded track already tried and found to be a picture (PGS / VobSub), without an index, or not Matroska (extraction.note_embedded_miss now also leaves the miss in the window property moransubs.embedded_miss for the chooser's process). Hebrew rows and pooled translations never carry it.
- Season packs (fetching/season_pack.py, bridge.download_inner): a download that unpacked several episodes' subtitles is recognised by its content, the PLAYING episode's file is delivered (the provider's "first file" used to be served for every episode), it is cached per episode (Cached_subs_v2 stem + ".S01E02") and the next episode's file (or the next season's first) is cached the same way and, when Hebrew, kept in season_pack/index.json, so the next episode's list offers it at once as a local file and picking the same pack there is a cache hit. When a pack holds several files for the same episode (a hearing-impaired copy, more than one release), a non-HI file beats an HI / SDH / CC copy and the closest release name beats the rest (season_pack.scan_folder). RAR archives are unpacked through Kodi's rar:// virtual file system when vfs.rar is available.
- Standalone: a video Kodi gives no ids and a file name for a title (the add-on installed alone, a plain file on stock Estuary) gets its title, year, season and episode from the release name (core/video_context.parse_release) and its IMDb id from TMDB, once per title (fetching/standalone_ids.py), kept for the session; Wizdom, YIFY and SubSource work for such a file.
- Verified without Kodi: contract 61/61 (1,414 golden cases re-recorded for the 26 chooser-row cases whose chips and release paint changed on purpose), 44 unit checks (.github/scripts/subs_contract/unit_session.py). Not tested in Kodi: rar://, the providers' answers to free text.

0.3.89
- The automatic subtitle on play runs again when the same file is played a second time in a row. autosub_service keeps the last file it handled (STATE['last_file']) because Kodi can fire onAVStarted more than once for one playback; nothing ever cleared it, so a file that was stopped and started again, or picked again from the list, got no automatic subtitle the second time -- no search, no embedded pick, no line in the log. It is cleared now when a playback stops, ends or fails and nothing is playing after it (playback_over; the player's onPlayBackStopped / onPlayBackEnded / onPlayBackError). Not when another file is already playing: that playback's own run has set the mark, and clearing it would let a repeated onAVStarted search again over a subtitle the viewer chose. Where the item's path differs between two starts of the same source (a debrid link resolved anew) the second start was never held back; a local file, or a link that resolves to the same address, was.
  Found while looking into a field report (16 Nov 2026) that a source with only an embedded subtitle is not translated automatically and has to be picked by hand. Whether this is that report's cause is not known: no log came with it. QA Kodi, a local file with an English and an Arabic text track under a name no provider knows (so the embedded pick is the only candidate), ai_when_no_hebrew on its default: the first start picked the embedded track by itself (resolve: kind=embedded_ai) and the Hebrew was on screen about 10 s later; before this change a second start of the same file did nothing at all; after it, three starts in a row each ran the pick and ended with the Hebrew stream on. The other known reasons for a pick left to the viewer are settings: 'AI translation when there is no Hebrew' on ask or manual, the automatic search off, or Kodi's subtitle languages without Hebrew.

Limits: twenty lines from two shows each; only lines that differ by inflection alone are compared; in 011 the reference is most likely the very translation the judges saw as the professional one.
